SOLUTION:
---------

1. INITIAL RECONNAISSANCE
   
   Started with quick ELF triage:
   - `file` -> 64-bit PIE, stripped Rust binary
   - `checksec` -> Full RELRO, NX, PIE
   - `strings` -> useful hardcoded artifacts:
     - `0149545b5f4b5d1e5c545d1a55036c5700404b46505d426e02001b4909030957414a7b7a48`
     - `112.105.110.103`
     - `112.111.110.103`
     - `IP Blocked!!! ...`
     - `Now you're pinging the pong!`

2. OBSERVE RUNTIME BEHAVIOR
   
   Running the program under `strace` shows:
   - UDP socket bind on `127.0.0.1:9768`
   - `recvfrom()` loop
   - prints `IP Blocked!!! ...` for invalid traffic

   This indicates the challenge is packet validation, not stdin input.

3. LOCATE THE VALIDATION ROUTINE
   
   Disassembly around the xrefs of the key strings shows:
   - Hex blob is decoded first into a 37-byte target buffer
   - Two dotted strings are parsed and reused as key material
   - Received datagram must have length exactly `0x25` (37)
   - Final check uses `bcmp` between transformed packet and target bytes

4. RECONSTRUCT THE TRANSFORM
   
   Let `target` be bytes decoded from the hardcoded hex string.

   Input packet (`msg`) is transformed in-place before comparison:
   - `msg[0] ^= key0[0]`
   - For `i = 1..36`:
     - use `key0` first, then `key1`
     - index with `i % len(key)`
     - toggle between keys whenever remainder is `0`

   In this binary, the effective key bytes are the ASCII bytes of:
   - `key0 = b"112.105.110.103"`
   - `key1 = b"112.111.110.103"`

5. INVERT THE CHECK
   
   Because the transform is XOR-based, inversion is direct:
   - `required_msg = target XOR same_key_schedule`

   Applying that gives:
   - `0xfun{h0mem4d3_f1rewall_305x908fsdJJ}`

6. NOTE ABOUT THE "IP BLOCKED" PATH
   
   There is an address gate in the packet path, so replaying from normal localhost
   traffic still hits the blocked message. Static RE of the transformation is the
   intended reliable path to recover the flag.
